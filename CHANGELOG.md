# Журнал изменений

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — по правилам из [дорожной карты](docs/ROADMAP.md#правила-версий-и-релизов): релиз на каждую версию x.y.z.

## [Не выпущено]

## [0.6.5] — 2026-09-30

Вход в панель через OIDC.

### Добавлено
- Вход в панель через OIDC (Google, Keycloak, Authentik и др.): код авторизации с PKCE, проверка подписи ID-токена (RS256, ES256), издателя, аудитории, срока и nonce. Включается флагами `serve -oidc-issuer`, `-oidc-client-id`, `-oidc-client-secret-file` (или `ZPT_OIDC_SECRET`), `-oidc-name`; адрес возврата — `<-url>/login/oidc/callback`.
- `zpt-controller user email -login ЛОГИН -email ПОЧТА` — привязка почты; войти через OIDC можно только под привязанной и подтверждённой провайдером почтой (новых пользователей вход сам не создаёт). Миграция схемы до версии 14.

### Как проверено
- Автотесты с поддельным провайдером: полный вход, непривязанная и неподтверждённая почта, токен для другого клиента, подделанная подпись и `alg: none`, вход без начатого сценария. С Google, Keycloak и Authentik не проверялось.

## [0.6.4] — 2026-09-30

Обзор и квоты.

### Добавлено
- Страница «Обзор» в панели: комнаты, участники, ждущие одобрения, устройства в сети, доля прямых соединений среди путей до пиров, число выходов в интернет, по комнатам; для администратора — счётчики relay (узлов, пакетов, ГБ с запуска).
- Схема комнаты на странице комнаты: участники, кто в сети, выходы, сети за узлами, линии к выбранному exit.
- Квоты: `zpt-controller serve -max-rooms N` (комнат на обычного пользователя; администраторов не касается) и `-max-members N` (участников в комнате; при переполнении вступление отклоняется).

### Как проверено
- Автотесты: квоты, подсчёты обзора, экранирование схемы, страница обзора. Трафик exit-узлов в обзор не входит.

## [0.6.3] — 2026-09-30

Двухфакторный вход в панель.

### Добавлено
- Двухфакторный вход в панель: TOTP-коды (RFC 6238, любое приложение-аутентификатор). Включается на странице «Мой аккаунт» по QR-коду с подтверждением кодом; для выключения нужен пароль. Код действует один раз (повтор отклоняется), допускается сдвиг часов на один шаг. Секрет шифруется KEK, если он задан. Миграция схемы базы до версии 13.
- `zpt-controller user totp-off -login ЛОГИН` — сбросить 2FA, если потерян телефон.

### Исправлено
- Ограничитель попыток входа хранил каждый спрашивавший адрес навсегда; теперь записи без недавних неудач удаляются.

### Как проверено
- Автотесты: векторы RFC 6238, окно и повтор кода, вход с 2FA и без, полный сценарий в панели, миграция со всех версий схемы. С реальными приложениями-аутентификаторами не проверялось.

## [0.6.2] — 2026-09-27

Подписанные релизы и обновление узла.

### Добавлено
- Релизы подписываются: к каждому прикладывается `release.json` (версия и SHA-256 всех файлов) и его подпись Ed25519 `release.json.sig`. Закрытый ключ хранится только в секрете репозитория и используется в процессе выпуска, открытый встроен в `zpt`.
- `zpt update [-check] [-channel stable|beta] [-yes]` — находит самый новый подписанный релиз канала и ставит его тем же способом, каким установлен узел: MSI поверх, deb/rpm через пакетный менеджер, из архива — замена `zpt` (и `zpt-tray` рядом) и перезапуск службы. Файл ставится, только если подпись манифеста сходится со встроенным ключом, версия в манифесте совпадает с релизом и новее установленной (откат подсунуть нельзя), а хеш файла совпадает с подписанным.
- Узел проверяет обновления раз в 12 часов (`update_channel: stable|beta|off` в конфиге) и сообщает о новой версии в журнале, `zpt status` (`update_available`) и трее — пункт «Установить обновление» запускает `zpt update` с запросом прав. Сам без подтверждения не устанавливает.
- `zpt status` показывает выключенные комнаты.

### Как проверено
- Автотесты на поддельном GitHub: выбор релиза по каналу (stable без предварительных версий, beta с ними), неподписанные релизы пропускаются, подмена файла после подписи, манифест от другой версии под новым тегом и чужой ключ — отклоняются; сравнение версий; замена бинарников из tar.gz и zip; пункт обновления в трее.
- Подпись в процессе выпуска проверяется на самом релизе 0.6.2 (манифест скачивается и проверяется встроенным ключом).
- Установка обновления поверх MSI и deb/rpm на реальных машинах **не проверялась** — впервые это станет возможно при переходе с 0.6.2 на следующую версию.

### Известные ограничения
- Версии до 0.6.2 обновляются только вручную.

## [0.6.1] — 2026-09-26

Трей-клиент.

### Добавлено
- `zpt-tray` — значок в области уведомлений (Windows; Linux со StatusNotifierItem): комнаты с вашим адресом и участниками (адрес, путь — напрямую / через ретранслятор / нет связи; клик копирует IP), выключение и включение комнат, выбор выхода в интернет (как решили админы / напрямую / любой разрешённый exit), вступление по приглашению из буфера обмена (через `zpt open` с подтверждением), окно с подробным состоянием. Цвет значка показывает состояние узла. Трей работает с правами пользователя, изменения делает `zpt` с запросом прав (UAC / polkit).
- Установщики ставят трей с автозапуском при входе в систему (MSI: ключ `Run` и ярлык в «Пуске»; deb/rpm: `/etc/xdg/autostart`).
- `zpt room off КОМНАТА` / `zpt room on КОМНАТА` — выключить комнату на этом устройстве, оставаясь участником, и включить обратно; выключенные комнаты — в `zpt status`.
- Канал управления только для чтения: `zpt status`, `rooms`, `peers` работают без прав администратора (`/run/zeropentime/status.sock`; на Windows `\\.\pipe\zeropentime-status`, открыт пользователям, вошедшим в систему). Менять что-либо по-прежнему может только администратор.
- В статусе пира — признак «админ разрешил как exit» (`exit_offered`).

### Исправлено
- Заметки к релизам на GitHub были пустыми: goreleaser с выключенным журналом изменений не брал текст и из `--release-notes`. Заметки всех прошлых релизов заполнены из CHANGELOG, конфигурация исправлена.
- Из MSI-сборки в релиз больше не попадают отладочные файлы `.wixpdb`.

### Как проверено
- Автотесты: меню трея строится из статуса (комнаты, пути, exit, выключенные комнаты, стабильность перерисовки), иконки PNG/ICO, буфер обмена Windows (в CI); канал статуса отвечает на `status` и не принимает `reload`, права канала Windows; сквозной тест — выключенная комната гаснет и возвращается, связь восстанавливается.
- CI: MSI ставит трей, автозапуск и ярлык; deb ставит трей и автозапуск (`desktop-file-validate`), `zpt status` работает без root.
- Трей запущен вручную на Windows 11: значок и меню «узел не отвечает». С работающим узлом, выбор exit и выключение комнат из меню на реальном рабочем столе, а также трей на Linux **не проверялись** вручную.

## [0.6.0] — 2026-09-26

Установщики: узел ставится одним файлом, а приглашение открывается кликом по ссылке.

### Добавлено
- MSI для Windows (amd64, arm64): `zpt.exe` и `wintun.dll` в `Program Files\zeropentime` (папка в `PATH`), служба «zeropentime» с автозапуском и перезапуском при сбое, конфиг `ProgramData\zeropentime\zpt.yaml` (не перезаписывается при обновлении и остаётся после удаления), обработчик ссылок `zpt://`. Обновление — установкой новой версии поверх.
- Пакеты deb и rpm (amd64, arm64): `/usr/bin/zpt`, служба systemd `zpt` (включается и запускается при установке, перезапускается при обновлении, останавливается при удалении), конфиг `/etc/zeropentime/zpt.yaml`, обработчик ссылок `zpt://` для рабочего стола.
- `zpt open ССЫЛКА` — так система открывает ссылки `zpt://`: показывает, в какую комнату и на какой контроллер (или к какому админу комнаты без контроллера) ведёт ссылка, запрашивает права администратора (UAC на Windows, pkexec на Linux) и вступает только после подтверждения — ссылку может подсунуть любая веб-страница.
- Контрольные суммы MSI — в `checksums-msi.txt` релиза.

### Изменено
- `zpt up` сам создаёт ключ узла при первом запуске (как `zpt join`): служба свежей установки работает ещё до первого приглашения.
- `zpt join` сразу просит работающий узел перечитать состояние — комната поднимается без ожидания очередной проверки.

### Как проверено
- В CI на каждом коммите: MSI ставится на чистый Windows-раннер, служба работает, `zpt status` отвечает через канал управления, `wintun.dll`, конфиг, `PATH` и обработчик `zpt://` на месте; после удаления служба и файлы программы удалены, конфиг остался. deb ставится на Ubuntu-раннер: служба включена и работает, `zpt status` отвечает, права `/etc/zeropentime` — 0700, файл обработчика ссылок проходит `desktop-file-validate`; после удаления служба остановлена, конфиг остался. rpm — проверка состава и скриптов.
- Открытие ссылки кликом в браузере (Windows и рабочие столы Linux) и запрос прав **не проверялись** вручную; MSI для arm64 и rpm только собираются, но не ставятся.

## [0.5.4] — 2026-09-26

Исправление падения узла в режиме userspace.

### Исправлено
- Узел в режиме `userspace: true` мог упасть целиком («send on closed channel») при остановке комнаты, если в этот момент закрывалось TCP-соединение внутри комнаты: встроенный сетевой стек (tun/netstack из amneziawg-go) закрывал канал пакетов, пока горутины gVisor ещё отправляли в него. Пакет скопирован в `internal/netstack` (MIT) с исправленным закрытием: сначала останавливается стек и дожидаются его горутины, канал больше не закрывается. Ошибка была во всех прошлых версиях; её поймали сквозные тесты CI на macOS при сборке 0.5.3.

### Как проверено
- Новый тест: 50 закрытий устройства во время отправки пакетов без паники; полный набор тестов, в том числе под `-race` в CI.

## [0.5.3] — 2026-09-26 (не опубликован)

Со-админы и адреса участников без контроллера: комната без сервера живёт, даже когда её владелец выключен.

> Сборка 0.5.3 не опубликована: тесты на коммите тега нашли падение узла в режиме userspace (см. 0.5.4). Используйте 0.5.4 — в ней всё из 0.5.3.

### Добавлено
- Карточки участников: каждый узел раз в минуту обменивается через gossip с парой соседей по комнате подписанными карточками — идентификатор узла, ключ disco и все его адреса (проброшенный порт, внешние адреса по STUN, адреса интерфейсов). Карточка подписана ключом самого узла и принимается только для участников из подписанного конфига комнаты; адреса остаются подсказками для disco. Так участники комнаты без контроллера находят друг друга (раньше каждый знал только владельца), а в комнатах с контроллером — новые адреса друг друга, пока контроллер недоступен (в дополнение к DHT из 0.5.1).
- Со-админы комнат без контроллера: `zpt room admin КОМНАТА УЧАСТНИК`. Флаг «админ» записывается в подписанный конфиг; узел со-админа сам забирает ключ подписи комнаты у другого админа через туннель — ключ выдаётся только адресам комнаты, которые конфиг называет админскими (адрес в комнате привязан туннелем к ключу участника). После этого со-админ приглашает (`zpt room invite`), принимает участников и меняет комнату без владельца.
- `zpt room members` показывает роль участника.
- Публичный STUN для узлов с комнатами без контроллера: внешний адрес узнаётся у `stun.l.google.com:19302` и `stun.cloudflare.com:3478`; свои серверы — `public_stun: [host:port, …]` в конфиге узла, выключить — `public_stun: [off]`.

### Исправлено
- Файл состояния узла (`state.json`) пишется через уникальный временный файл, а замена и чтение повторяются несколько миллисекунд, если файл занят: на Windows одновременная запись из `zpt` и службы или чтение во время замены могли давать ошибку.

### Изменено
- Владелец новой комнаты без контроллера отмечен в конфиге как админ; в комнатах из 0.5.2 это делает первая команда `zpt room admin`.

### Как проверено
- Сквозные тесты: трое в комнате без контроллера — участники, знавшие только владельца, получают карточки друг друга и связываются напрямую, связь остаётся после выключения владельца (без карточек тест падает); со-админ получает ключ подписи, при выключенном владельце принимает нового участника по своему приглашению, обычному участнику ключ не выдаётся.
- Юнит-тест проверки карточек: чужая подпись, чужой идентификатор, изменённые адреса, другая комната, устаревшая карточка — отвергаются.
- На реальных машинах в разных сетях и с публичными STUN-серверами **не проверялось**.

### Известные ограничения
- Отнять права со-админа нельзя без пересоздания комнаты: ключ подписи уже у него.
- Если два админа одновременно изменят комнату, у части участников может остаться одна из двух версий с одинаковым номером до следующего изменения.
- Ретранслятора у комнаты без контроллера по-прежнему нет.

## [0.5.2] — 2026-09-26

Комнаты без контроллера: узел сам создаёт комнату, подписывает её конфиг и принимает участников по приглашению.

### Добавлено
- `zpt room create -local -name ИМЯ [-me ИМЯ_В_КОМНАТЕ] [-subnet 10.100.7.0/24]` — комната без сервера. Узел-владелец создаёт ключ подписи комнаты (Ed25519) и подписывает её конфиг сам — так же, как это делает контроллер; остальные участники проверяют подпись закреплённым ключом.
- `zpt room invite КОМНАТА [-uses 1] [-hours 24] [-endpoint host:port]` — приглашение-ссылка `zpt://local?…` (секрет комнаты, ключ подписи, одноразовый токен, адреса владельца). По умолчанию адреса берутся автоматически: проброшенный порт, внешние адреса, найденные через STUN контроллеров, и адреса сетевых интерфейсов.
- `zpt join "zpt://local?…"` — вступление: узел просит владельца принять его через disco (запрос подписан ключом узла), владелец проверяет токен, выдаёт адрес в комнате и подписывает новую версию конфига; новичок поднимает комнату с владельцем и забирает подписанный конфиг через gossip.
- `zpt room list`, `zpt room members КОМНАТА`, `zpt room kick КОМНАТА УЧАСТНИК` — список комнат без контроллера, участники, исключение (новая версия конфига расходится через gossip).
- Запросы на вступление ограничены по частоте; неизвестная комната — молчание, чтобы не выдавать её существование.

### Исправлено
- Gossip после новой версии конфига объявлял её один раз и потом только через 20 с: если этот пакет терялся (например, на смене сессии туннеля), участник узнавал об отзыве с задержкой. Теперь новая версия объявляется ещё трижды с шагом 2 с. Сквозной тест отзыва через gossip иногда падал, теперь 10 из 10 прогонов проходят.
- Сокеты gossip закрываются до остановки комнаты (гонка при закрытии встроенного сетевого стека в тестах).

### Как проверено
- Сквозной тест: владелец создаёт комнату, второй узел вступает по ссылке, получает подписанный конфиг, обмен трафиком работает; одноразовое приглашение израсходовано; исключение убирает участника у владельца.
- Разбор и сборка ссылки, сообщения вступления в disco — автотесты.
- На реальных машинах в разных сетях (NAT с обеих сторон) **не проверялось**.

### Известные ограничения
- Участник знает адреса только владельца: участники связываются друг с другом напрямую, лишь если владелец передал им адреса при вступлении; обмен адресами между всеми участниками через gossip — в 0.5.3.
- Принимать участников может только владелец, и только пока его узел запущен и доступен. Со-админы — в 0.5.3.
- Ретранслятора (relay) у комнаты без контроллера нет: нужен прямой путь или проброшенный порт хотя бы у владельца.

## [0.5.1] — 2026-09-26

DHT: участники находят друг друга без контроллера.

### Добавлено
- Настройка комнаты «Поиск участников через DHT без контроллера» (панель, `zpt-controller room set -room R -dht on`). В такой комнате каждый узел раз в 10 минут объявляет свой внешний UDP-порт в публичной DHT BitTorrent под ключом `SHA1(секрет комнаты ‖ сутки)` — без секрета запись не связать с комнатой, ключ меняется каждые сутки — и ищет остальных. Найденные адреса — только подсказки для поиска пути (disco): отвечает лишь участник с нужным ключом, подделать участника через DHT нельзя.
- Свой минимальный клиент DHT (BEP 5, запросы read-only по BEP 43) без сторонних зависимостей; общеизвестные bootstrap-узлы (router.bittorrent.com и другие). Трафик DHT идёт мимо exit-туннеля.

### Исправлено
- Gossip из 0.5.0 при подъёме комнаты сразу слал объявление соседу, и оба узла начинали рукопожатие одновременно — первая попытка срывалась, и связь в комнате появлялась через 5–15 с (обходил защиту от встречных рукопожатий из 0.1.1). ## [0.3.3] — 2026-09-26

Kill switch: без exit — без интернета.

### Добавлено
- `zpt exit -kill-switch [-allow-lan] КОМНАТА УЧАСТНИК`: пока выбранный exit недоступен (выключен, отозван, нет связи), весь интернет-трафик устройства блокируется, а не уходит напрямую; комнаты, собственные соединения узла (контроллер, relay, VLESS), DHCP и loopback работают. `-allow-lan` оставляет доступной свою локальную сеть, broadcast и multicast. Для exit, назначенного админом, — `kill_switch` и `kill_switch_allow_lan` в конфиге узла.
- Linux: правила nftables (`inet zpt_killswitch`) переживают сбой узла — интернет остаётся закрытым; `zpt exit off` / `auto` снимают их и без работающего узла.
- Windows: брандмауэр WFP из wireguard-windows (MIT, перенесён в `internal/wgfirewall`) с доработками: разрешены все интерфейсы комнат и сети LAN; правила обновляются без окна без защиты и снимаются Windows при завершении узла.
- Контроллер передаёт назначенный админом exit и после его отзыва — иначе kill switch выключался бы как раз тогда, когда нужен.

### Как проверено
- NAT-стенд в CI на настоящих TUN (Linux): с kill switch после отзыва exit A не выходит в интернет ни через B, ни напрямую, но комната работает и локальная сеть закрыта; после повторного одобрения интернет через B возвращается за единицы секунд (≤ 10 с); с `-allow-lan` локальная сеть доступна, интернет — нет; `zpt exit off` возвращает прямой путь и снимает правила.
- Kill switch на Windows (WFP) **не проверялся** — в CI его не поднять без риска отрезать раннер.

### Известные ограничения
- На Windows правила WFP снимаются, если узел упал (система закрывает сессию), — защита не переживает сбой узла.

Одновременно интернет идёт только через одну комнату.

Собственные соединения узла (туннель, контроллер, VLESS, DNS-запросы узла) помечаются fwmark и идут напрямую; метка переносится на ответы через conntrack, чтобы их не отбрасывал rp_filter.
- Exit-узел на Linux: пересылка и masquerade в интернет через nftables; локальные и служебные сети exit-узла (10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16) участникам закрыты, если это не разрешённые маршруты subnet router.

### Изменено
- База контроллера: миграция 7.

### Как проверено
- Сквозной тест: exit без одобрения нельзя ни разрешить, ни назначить; после одобрения маршрут по умолчанию к exit появляется только после выбора в панели; `zpt exit off` отменяет выбор админа, `zpt exit КОМНАТА УЧАСТНИК` включает, отзыв exit убирает.
- NAT-стенд в CI на настоящих TUN (Linux): веб-сервер «в интернете» видит A с адреса NAT узла A, после выбора exit — с адреса NAT узла B; при этом комната и связь с контроллером работают, сеть за B недоступна; после отзыва и после `zpt exit off` трафик возвращается на прямой путь, правила маршрутизации сняты.
- С реальными провайдерами и дистрибутивами с другими настройками брандмауэра **не проверялось**.

### Известные ограничения
- Выходить через exit пока можно только с Linux (Windows — 0.3.2), exit-узлом — только Linux.
- DNS-запросы и IPv6 идут мимо exit (защита от утечек — 0.3.2); при пропаже exit интернет не блокируется (kill switch — 0.3.3).

- Сервер VLESS вынесен в отдельный пакет: узел не содержит серверной части REALITY.

### Исправлено
- Если relay отвечал раньше, чем пробивался NAT, узел оставался на relay до 20 с, прежде чем перейти на прямой путь. Теперь первую минуту прямой путь ищется каждые 2 с. (Релиз 0.2.1 был опубликован при красном CI из-за этой проблемы — NAT-стенд увидел путь через relay вместо прямого; связь при этом работала.)

### Как проверено

## [0.2.1] — 2026-09-26

Связь через любой NAT: пробивка NAT и relay. (Шаги 0.2.1 и 0.2.2 дорожной карты вышли одним релизом — код пересекается; дальнейшие номера сдвинуты.)

### Добавлено
- **Поиск пути (disco):** узлы обмениваются зашифрованными ping/pong по всем известным адресам друг друга — локальным, проброшенному, от STUN, тем, откуда пришли пакеты. Самый быстрый рабочий путь (локальная сеть в приоритете) становится адресом пира в AmneziaWG; пока пути нет, оба узла пробуют каждые 2 с — это и пробивает NAT. Отвечаем только узлам из своих комнат, отправитель аутентифицирован, пакеты выглядят как случайные байты.
- **Relay в контроллере** (UDP 3480, флаги `-relay` и `-relay-public`): когда прямой путь невозможен (симметричный NAT, закрытый UDP к пиру), трафик идёт через relay. Relay видит только зашифрованные пакеты AmneziaWG, пересылает лишь между участниками общей комнаты, ограничивает частоту кадров. Кадры relay тоже выглядят как случайные байты. Прямой путь всегда в приоритете: пока пир доступен только через relay, прямые пути продолжают проверяться.
- Панель: для каждого участника — сколько пиров он видит напрямую и сколько через relay.
- `zpt-controller room create|list` и `invite create` — комнаты и приглашения из командной строки.
- **NAT-стенд в CI:** Linux network namespaces, NAT-роутеры на nftables, настоящие TUN-интерфейсы. Проверяет: через два конусных NAT — прямая связь, с симметричным NAT — связь через relay, тип NAT определяется верно.

### Изменено
- База контроллера: миграции 3 и 4 (ключ disco узла, настройки, ключ relay).
- Docker: порт relay 3480/udp.

### Как проверено
- Автотесты: форматы disco и relay (подмена отправителя, подделка, чужие сессии, фаззинг); relay пересылает только между участниками общей комнаты, следует за сменой адреса узла; сквозные тесты — неверный «локальный» адрес у обоих узлов (disco находит рабочий путь за ≈1,5 с, без disco связи нет) и полностью закрытый прямой путь (трафик идёт через relay, панель это показывает).
- NAT-стенд в CI с настоящими TUN на Linux: конусный ↔ конусный — напрямую; конусный ↔ симметричный и симметричный ↔ симметричный — через relay.

### Известные ограничения
- Relay только встроенный в контроллер; отдельные relay-серверы (`zpt relay`) и сертификаты участников для них — позже.
- Если UDP к relay заблокирован целиком, связи нет — VLESS + Reality по TCP/443 будет в 0.2.2.

### Как проверено
- Автотесты на Linux, Windows и macOS: сквозные сценарии (контроллер и несколько узлов, приглашение → одобрение → трафик → исключение за ~50 мс, две комнаты на узле, блокировка, отказ при подмене ключа комнаты, отсутствие открытого текста и сигнатур на проводе) — на встроенном сетевом стеке, без системных интерфейсов.
- **На реальных сетевых интерфейсах Windows и Linux этот выпуск не проверялся** — проверка перенесена в 0.1.1.

### Известные ограничения
- Устройства должны видеть друг друга напрямую: одна локальная сеть, публичный IP или проброшенный UDP-порт. Прохождение NAT и relay — в 0.2.
- Windows: `wintun.dll` не входит в архив — положите его рядом с `zpt.exe` (https://www.wintun.net); `zpt up` запускается от администратора; интерфейсы комнат получают профиль «Общедоступная сеть», и брандмауэр блокирует входящие ping/SMB. Всё это — в 0.1.1.
- Ключи подписи комнат хранятся в базе контроллера без шифрования (запланировано в 0.4.3).
- AmneziaWG закреплён на master-коммите `457d920` (AWG 3): релизного тега 3.x пока нет.
