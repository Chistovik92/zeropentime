# zeropentime

Открытая децентрализованная замена ZeroTier: **комнаты = виртуальные локальные сети**. Одно устройство может быть в нескольких комнатах одновременно.

- Шифрование и транспорт — **AmneziaWG 3** (форк WireGuard с защитой от DPI): Noise IK, Curve25519, ChaCha20-Poly1305 + PSK комнаты.
- Маскировка: защита заголовков AWG 3, случайные типы сообщений (H1–H4), паддинги (S1–S4), мусорные пакеты, content padding и скрытая метка комнаты вместо открытого номера.
- Все комнаты узла работают через **один UDP-порт**.

Документы: [архитектура](docs/ARCHITECTURE.md), [план реализации](docs/PLAN.md), [дорожная карта по версиям](docs/ROADMAP.md).

> Статус: **0.3** — контроллер с админ-панелью, приглашения, подписанные конфиги комнат; связь через любой NAT (STUN, UPnP / NAT-PMP, пробивка NAT, relay, VLESS + REALITY при блокировке UDP); broadcast и mDNS для LAN-игр; доступ к сети за узлом. Дальше — выход в интернет через узел комнаты; см. [дорожную карту](docs/ROADMAP.md).

## Сборка

```bash
go build -o zpt ./cmd/zpt                        # узел
go build -o zpt-controller ./cmd/zpt-controller  # контроллер с админ-панелью
```

Нужен Go 1.26+. Готовые сборки — на странице [релизов](https://github.com/Chistovik92/zeropentime/releases); архив для Windows уже содержит `wintun.dll`. При сборке из исходников положите `wintun.dll` (https://www.wintun.net) рядом с `zpt.exe` или выполните `bash scripts/fetch-wintun.sh`.

## Контроллер и админ-панель

```bash
zpt-controller useradd -db controller.db -login admin -admin
zpt-controller serve -db controller.db -listen :8080 -url https://zpt.example.org
```

Панель: `https://zpt.example.org` → войти → создать комнату → «Создать приглашение». Откройте также UDP 3478 и 3479 (встроенный STUN: узлы узнают свой внешний адрес) и UDP 3480 (встроенный relay: пересылка, когда прямой путь невозможен). Для HTTPS используйте `-tls-cert/-tls-key` или обратный прокси с `-trust-proxy` (готовый вариант с Caddy: [deploy/docker-compose.yml](deploy/docker-compose.yml)).

Что умеет панель:
- комнаты: создание (подсеть выбирается автоматически или вручную), переименование, режим вступления (с одобрением / автоматически), удаление;
- участники: онлайн-статус, внешний IP, одобрение, блокировка, исключение, смена имени, IP и тегов;
- приглашения: лимит использований, срок, «без одобрения», заметка, ссылка + QR-код (показываются один раз), отзыв;
- пользователи (для админа), смена пароля, журнал всех действий.

Забыли пароль: `zpt-controller passwd -db controller.db -login admin`.

### Если у участников блокируют UDP: VLESS + REALITY

Контроллер может принимать трафик relay через VLESS внутри REALITY на TCP/443. Для наблюдателя это TLS 1.3 к настоящему сайту (его сертификат подставляется), а любой, кто подключится без ключа, попадёт на этот сайт.

```bash
zpt-controller serve -db controller.db -url https://zpt.example.org \
  -vless :443 -vless-dest www.microsoft.com:443
```

`-vless-dest` — сайт, который будет имитироваться: с TLS 1.3, не за вашим доменом. Ключи REALITY и VLESS создаются автоматически и раздаются узлам. Узлы переходят на VLESS сами, если UDP до relay не отвечает (или всегда — `relay_transport: vless` в конфиге узла). Порт 443 должен быть свободен: в docker-compose с Caddy используйте другой порт, например `-vless :8443`, либо отдельный сервер.

### В Docker

Готовый образ (linux/amd64, linux/arm64): `ghcr.io/chistovik92/zeropentime-controller`.

```bash
docker run -d --name zpt -p 8080:8080 -v zpt-data:/data ghcr.io/chistovik92/zeropentime-controller serve -db /data/controller.db -listen :8080 -url https://zpt.example.org
docker exec zpt zpt-controller useradd -db /data/controller.db -login admin -admin
```

С автоматическим HTTPS через Caddy — [deploy/docker-compose.yml](deploy/docker-compose.yml):

```bash
ZPT_DOMAIN=zpt.example.org docker compose -f deploy/docker-compose.yml up -d
```

## Узел: вступить в комнату

```bash
zpt join "zpt://join?c=...&r=...&k=...&t=..."
zpt up
```

`zpt join` создаёт ключ узла (если его нет) и запоминает контроллер. `zpt up` (Windows — от администратора, Linux — root) поднимает все комнаты, в которых узел одобрен, и дальше сам следит за изменениями: новые участники, исключения и одобрения применяются за секунды, без перезапуска. Выйти: `zpt leave ID_КОМНАТЫ`.

Если контроллер недоступен, уже работающие комнаты продолжают работать.

На Windows интерфейсы комнат автоматически получают профиль сети «Частная», чтобы брандмауэр пропускал ping, общие папки и обнаружение устройств, как в домашней сети.

## Доступ к сети за узлом

Чтобы участники комнаты видели устройства вашей домашней или офисной сети (принтер, NAS, камеры), добавьте в конфиг узла, который стоит в этой сети (пока только Linux):

```yaml
advertise_routes: [192.168.1.0/24]
```

Затем админ комнаты нажимает «Разрешить сети» у этого участника в панели (или `zpt-controller routes approve -db controller.db -room ID -member ИМЯ`). Устройствам в сети ничего настраивать не нужно.

## Безопасность

- Трафик: AmneziaWG (Curve25519, ChaCha20-Poly1305) + PSK комнаты + маскировка AWG 3.
- Конфиг комнаты подписан ключом комнаты (Ed25519); узел закрепляет этот ключ из приглашения и отвергает конфиги с другой подписью или более старой версией.
- Запросы узлов подписаны ключом узла; ответы контроллера зашифрованы на ключ узла (NaCl box) — секреты комнат не видны даже без TLS.
- Ключ узла и `state.json` доступны только владельцу, администраторам и системе (на Windows — защищённый ACL, на Linux — права 0600).
- Панель: пароли Argon2id, сессии HttpOnly, CSRF-токены, CSP, ограничение попыток входа, журнал действий.

## Статические комнаты без контроллера

Для двух-трёх устройств без сервера: `zpt room new` → секрет, комнаты и пиры описываются в YAML по [примеру](deploy/examples/zpt.yaml), публичные ключи — `zpt pubkey -c zpt.yaml`, запуск — `zpt up -c zpt.yaml`.

## Тесты

```bash
go test ./...
```

Сквозные тесты `internal/e2e` поднимают контроллер и несколько узлов в одном процессе: приглашение → одобрение → трафик → исключение (распространяется за доли секунды), две комнаты на узле, блокировка, отказ при подмене ключа комнаты.

Сквозной тест `internal/node` поднимает два узла с двумя комнатами на встроенном сетевом стеке (без прав администратора), пропускает трафик через «прослушивающий» прокси и проверяет, что:
- данные доходят в обеих комнатах, а комнаты изолированы;
- в перехваченных пакетах нет открытого текста;
- у пакетов нет постоянного префикса (сигнатуры для DPI);
- узел без разрешения или с неверным секретом комнаты не может подключиться.
