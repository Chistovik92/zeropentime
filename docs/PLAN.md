## 1. Окончательные технические решения

### 1.1 Data plane: AmneziaWG 3 через `amneziawg-go`, свою криптографию не пишем
- Шифрование и сессии — **`github.com/amnezia-vpn/amneziawg-go`** (userspace-форк wireguard-go). Криптография та же, что у WireGuard (Noise IK, Curve25519, ChaCha20-Poly1305), плюс маскировка от DPI.
  - Используем возможности AWG 3: защиту заголовков (`header_protection_key`), диапазоны типов сообщений H1–H4, паддинги S1–S4, мусорные пакеты Jc/Jmin/Jmax, пакеты-«подписи» I1–I5, `content_padding_addition`.
  - Версия: у `amneziawg-go` нет тега AWG 3.x (последний тег `v1.0.4` — AWG 1.5/2.0). Закреплён коммит `457d920` из `master` (24.07.2026), в котором есть AWG 3. Как только появится релизный тег — переходим на него.
- **Секрет комнаты** (32 байта) — единственное, что делят участники комнаты. Из него через HKDF выводятся: H1–H4 (4 непересекающихся диапазона), S1–S4 (≥ 12 — минимум AWG для защиты заголовков), ключ защиты заголовков, **PSK** (второй слой шифрования: без секрета комнаты рукопожатие не завершится даже с правильным ключом) и ключ метки комнаты. Клиентские параметры (Jc, Jmin, Jmax, I1–I5, content padding) — по умолчанию или из конфига.
- TUN: `amneziawg-go/tun` (Linux `/dev/net/tun`, Windows **Wintun**, macOS `utun`).
- **Одно AWG-устройство на каждую комнату** → своё TUN-устройство, свой IP и изоляция средствами ОС.
- **Один UDP-сокет на весь узел** (`internal/magicsock`, свой `conn.Bind`):
  - перед каждым пакетом — **скрытая метка комнаты** 8 байт: `nonce(4 случайных) ‖ AES-128(ключ_метки, nonce)[:4]`. Для наблюдателя это случайные байты; открытого номера комнаты на проводе нет, поэтому маскировка AWG не ломается;
  - приёмник проверяет метку по ключам своих комнат (одна операция AES на комнату) и отбрасывает всё чужое ещё до AWG — это же отсекает сканеры;
  - итог: одна NAT-дыра между двумя узлами обслуживает все их общие комнаты.
- Ключ AWG у узла свой для каждой комнаты (HKDF от identity и ID комнаты): утечка ключа одной комнаты не затрагивает другие.
- MTU комнаты по умолчанию 1380: 1380 + 32 (AWG) + S4 ≤ 32 + метка 8 + UDP/IPv6 48 = 1500.

### 1.2 Broadcast/multicast поверх WireGuard
WireGuard не передаёт broadcast. Решение — обёртка над TUN (`tun.Device` wrapper):
1. Демон читает исходящий пакет из TUN. Если это broadcast (`255.255.255.255`, broadcast подсети) или multicast (`224.0.0.0/4`: mDNS, SSDP, LLMNR) —
2. упаковывает его в unicast UDP на `overlay-IP пира:4797` (служебный порт) для каждого онлайн-пира комнаты. Такие пакеты идут через WireGuard и шифруются;
3. демон-получатель принимает их на служебном порту и **инжектит исходный пакет** в свой TUN.
- Лимит скорости broadcast (по умолчанию 200 pps на комнату), чтобы шторм не положил сеть.
- Настройка на комнату: `broadcast: on|off|mdns-only`.

### 1.3 Интернет через комнату (exit node) — F6
**Сторона exit-узла**
- В панели или через `zpt exit advertise --room X` узел предлагает себя как exit. Админ комнаты одобряет, ACL-тег `exit-user` определяет, кто может им пользоваться.
- Linux: `net.ipv4.ip_forward=1`, `net.ipv6.conf.all.forwarding=1`, nftables `masquerade` с TUN комнаты на внешний интерфейс. Правила ставит демон в свою таблицу `zpt` и снимает при остановке.
- Windows exit: **userspace NAT на gVisor netstack** (как `tailscale` netstack mode). Системный NAT Windows (WinNAT/ICS) ненадёжен, поэтому на него не опираемся. Linux-exit — в MVP, Windows-exit — в фазе 3.
- Лимиты: полоса на клиента и общая (настраиваются в панели).

**Сторона клиента**
- `zpt exit use <node> --room X` или переключатель в GUI.
- В AWG-устройстве комнаты этому пиру ставится `AllowedIPs += 0.0.0.0/0, ::/0`.
- Маршруты:
  - Linux: policy routing (`ip rule` + отдельная таблица, fwmark на собственный UDP-сокет демона — классическая схема wg-quick);
  - Windows: маршруты `0.0.0.0/1` + `128.0.0.0/1` через Wintun, исключения `/32` для адресов relay и эндпоинтов пиров через исходный шлюз. Сокет демона привязан к физическому интерфейсу (`IP_UNICAST_IF`), чтобы не было петли.
- **DNS**: при включённом exit системный DNS переключается на резолвер демона (`100.100.x.53` внутри overlay), который шлёт запросы через exit-узел. На Windows — NRPT + метрика интерфейса, на Linux — systemd-resolved (`resolvectl`) или `/etc/resolv.conf`.
- **Kill switch**: если exit отключился, трафик в интернет блокируется (Windows — WFP-фильтры, Linux — nftables), пока пользователь не выключит exit.
- **Доступ к своей LAN** (`--allow-lan`): локальная подсеть не заворачивается в exit, чтобы принтер/роутер оставались доступны.
- Защита от IPv6-утечек: если exit не умеет IPv6 — IPv6 в интернет блокируется.

### 1.4 Subnet router — F7
- Узел объявляет `routes: [192.168.1.0/24]`, админ одобряет.
- У остальных участников этот префикс добавляется в `AllowedIPs` пира и в маршруты ОС.
- На роутере — forwarding + masquerade, как у exit, но только для объявленного префикса.
- Конфликт префикса с локальной сетью клиента → предупреждение, маршрут не ставится.

### 1.5 Control plane
- **Идентичность**: Ed25519-ключ узла, `NodeID = base32(blake2s(pub))[:16]`.
- **Комната**: корневой ключ Ed25519, `RoomID = hash(root_pub)`. Корневой ключ подписывает `AdminCert` для админов.
- **MemberCert** (подписан админом): `room_id, node_pub, wg_pub, ip4, ip6, tags, routes, exit_allowed, not_after` — срок 7 дней, авто-продление за 2 дня до истечения.
- **RoomConfig** (подписан, монотонная `version`): подсеть, ACL, DNS-записи, список отозванных, одобренные exit-узлы и маршруты, настройки broadcast.
- Формат — **protobuf** с детерминированной сериализацией под подписью.
- Каналы доставки (по приоритету): WebSocket-стрим контроллера → gossip от пиров комнаты → DHT. Узел принимает только корректно подписанный конфиг с бо́льшей `version`.

### 1.6 NAT traversal и relay
- **disco-протокол** (по образцу Tailscale): маленькие пакеты с подписью Noise-box между узлами — ping/pong/call-me-maybe. Узлы обмениваются кандидатами-эндпоинтами (локальные IP, STUN-адрес, UPnP-порт) через relay или контроллер и одновременно пробивают NAT.
- **STUN** на каждом relay (`pion/stun` для клиента, свой простой сервер).
- **UPnP/NAT-PMP/PCP** — `huin/goupnp` + `jackpal/go-nat-pmp`.
- **Relay** (в стиле DERP): UDP-режим + **VLESS + Reality по TCP/443** для сетей, где UDP заблокирован или режется. Для DPI это TLS-сессия к легитимному сайту (Reality заимствует его сертификат), внутри — те же AWG-пакеты с метками комнат, то есть сквозное шифрование AWG сохраняется, а VLESS — только внешняя обёртка. Реализация — `github.com/xtls/xray-core` как библиотека в `internal/relay/vless`; клиент автоматически переключается UDP → VLESS после неудачных попыток и периодически пробует вернуться на UDP. Relay пересылает уже зашифрованные WireGuard-пакеты по NodeID; обслуживает только узлы, предъявившие валидный MemberCert любой комнаты, известной relay, или токен инстанса.
- Постоянный апгрейд: через relay — сразу, параллельно попытки direct каждые 30 с.
- Relay-карта: список relay с регионами из контроллера + публичные relay из bootstrap-списка. Клиент выбирает домашний relay по наименьшему RTT.

### 1.7 Децентрализованный поиск (фаза 4)
- `go-libp2p-kad-dht`: запись `hash(RoomID‖NodeID) → подписанные эндпоинты + домашний relay`, TTL 10 мин.
- Controller-in-client: `zpt room create --local` — контроллер работает в демоне владельца; состояние комнаты реплицируется всем со-админам (подписанный журнал изменений, last-writer-wins по версии).

### 1.8 ACL — F8
- Политика в RoomConfig: `[{src: tag|node|*, dst: tag|node|*, proto: tcp|udp|icmp|*, ports: "22,80,1000-2000", action: allow|deny}]`, по умолчанию allow-all внутри комнаты (можно поменять на deny-all).
- Применяется в обёртке TUN **на принимающей стороне** (stateful: ответы на разрешённые соединения пропускаются, conntrack в памяти).
- Exit и subnet-маршруты — отдельные права (`exit_allowed`, `routes_allowed`).

### 1.9 DNS — F9
- Встроенный резолвер демона (`miekg/dns`) на `100.100.0.53` (magic IP в каждом TUN).
- Зона `*.<room>.zpt` из RoomConfig; остальное — в системный upstream или через exit.
- Windows: NRPT-правило для суффикса `.zpt`; Linux: `resolvectl dns/domain` на интерфейс.

## 3. Фазы и задачи

Оценки — для 1–2 разработчиков. У каждой фазы есть **демо-критерий**: фаза не закрыта, пока он не проходит в e2e-тестах.

### Фаза 0 — Скелет и прототип data plane (2 недели)
- [x] Go-модуль, `cmd/zpt`, CI на GitHub Actions (Linux, Windows, macOS).
- [ ] golangci-lint, goreleaser-заготовка.
- [x] `identity`: генерация и хранение ключа, NodeID, ключи AWG по комнатам.
- [ ] Права на файл ключа в Windows (ACL только SYSTEM/Администраторы).
- [x] `obfs`: секрет комнаты → параметры AWG 3, PSK, скрытая метка комнаты.
- [x] `room` + `amneziawg-go`: TUN с IP из статического YAML (Windows/Linux/macOS), пиры из YAML; userspace-режим на gVisor.
- [x] `magicsock` v0: один UDP-сокет, скрытые метки комнат, несколько комнат на узле.
- [x] Сквозные тесты: две комнаты, изоляция, отсутствие открытого текста и сигнатур на проводе, отказ чужим узлам.
- [ ] Windows: служба (`golang.org/x/sys/windows/svc`), установка Wintun, профиль сети «Частная».
- [ ] Ручная проверка на реальных интерфейсах: Windows + Linux через интернет.

**Демо**: два узла (Win + Linux) в одной LAN, две комнаты из статического конфига, ping и iperf3 в обеих, комнаты изолированы.

### Фаза 1 — Контроллер, PKI, панель v1 (4 недели)
- [x] Формат протокола: JSON-документы с подписью Ed25519 поверх сырых байт (без канонизации, без кодогенерации). Protobuf отложен — пока не нужен.
- [x] `pki`: подписанный `RoomConfig` (закрепление ключа комнаты из приглашения, защита от отката версии), подписанные запросы узлов, ответы контроллера зашифрованы на ключ узла (NaCl sealed box).
- [ ] `MemberCert` — отдельный сертификат участника для relay и gossip (нужен в фазах 2 и 4).
- [x] `store`: SQLite (без CGO), схема User, Session, Node, Room, Member, Invite, Audit.
- [ ] Postgres (опционально) и миграции схемы между версиями.
- [x] `controller`: создание комнаты (автовыбор подсети /24 из `10.128.0.0/9`), инвайты, join → pending/active, выдача IP, long-poll вместо WebSocket (проще и проходит любые прокси).
- [x] Авторизация: Argon2id, сессии, CSRF, CSP, rate limit на вход; первый админ — `zpt controller useradd -admin`.
- [x] Панель v1 (серверные HTML-шаблоны, встроены в бинарник): комнаты, участники (одобрить/заблокировать/исключить/IP/теги/имя), инвайты (ссылка + QR), пользователи, смена пароля, журнал.
- [x] CLI: `zpt join`, `zpt leave`, `zpt up`, `zpt controller serve|useradd|passwd`.
- [ ] CLI `zpt status`/`zpt peers` — нужен локальный IPC с демоном.
- [x] Узел применяет конфиг «на лету»: пиры меняются диффом, сессии не рвутся.
- [x] Dockerfile + docker-compose с Caddy (HTTPS).
- [ ] Хранение ключей подписи комнат зашифрованными (KEK) и бэкап.

**Демо**: e2e — контроллер, 3 узла, приглашение → одобрение → трафик; исключение доходит до всех узлов ≤ 5 с (в тесте ~50 мс). ✅ (в userspace-режиме; ручная проверка на реальных интерфейсах — вместе с фазой 0)

### Фаза 2 — NAT traversal, relay, «локалка» (4 недели)
- [ ] `relay`-сервер: UDP + VLESS/Reality на 443, авторизация по сертификату (VLESS UUID выдаётся контроллером на узел), лимиты, метрики; встроен в `zpt controller`, может работать отдельно (`zpt relay`).
- [ ] Клиентский транспорт VLESS + Reality в magicsock: автопереключение UDP → VLESS и обратно.
- [ ] STUN-сервер на relay, STUN-клиент в узле, определение типа NAT.
- [ ] `disco`: обмен кандидатами, одновременная пробивка, выбор лучшего пути, апгрейд relay → direct, keepalive 25 с.
- [ ] UPnP / NAT-PMP / PCP.
- [ ] `tunwrap`: broadcast/multicast-эмуляция, rate limit.
- [ ] Панель: для каждого пира direct/relay, RTT, трафик; страница relay-серверов.
- [ ] e2e-стенд: Linux network namespaces + nftables для эмуляции full-cone, restricted, port-restricted, symmetric NAT и «только TCP 443».

**Демо**: e2e — все пары типов NAT соединяются (симметричный↔симметричный — через relay); LAN-игра с поиском по broadcast (тест: утилита, шлющая UDP-broadcast) и mDNS-обнаружение между Windows и Linux через интернет.

### Фаза 3 — Интернет и сети за узлом (4 недели)
- [ ] `router/linux`: policy routing, fwmark, forwarding, nftables masquerade.
- [ ] `router/windows`: маршруты `/1`, исключения для эндпоинтов, привязка сокета к физическому интерфейсу, метрики интерфейсов.
- [ ] Exit node: объявление → одобрение в панели → выбор на клиенте (CLI + панель «мои устройства»).
- [ ] DNS через exit, защита от утечек DNS/IPv6.
- [ ] Kill switch (nftables / WFP).
- [ ] `--allow-lan`.
- [ ] Subnet router: объявление маршрутов, одобрение, конфликты префиксов.
- [ ] Windows-exit через gVisor netstack.
- [ ] Лимиты полосы на exit.

**Демо**: Windows-клиент выбирает Linux-exit в другой стране → `curl ifconfig.me` показывает IP exit; dnsleaktest не видит DNS провайдера клиента; выдернули exit → интернет блокируется (kill switch), вернули → восстановился ≤ 10 с. Из комнаты открывается веб-интерфейс домашнего роутера через subnet router.

### Фаза 4 — ACL, DNS, децентрализация (4 недели)
- [ ] `acl`: движок stateful-фильтра в tunwrap, редактор правил в панели (таблица + JSON), тест «что если» (src → dst:port → allow/deny).
- [ ] `dns`: magic DNS, `имя.комната.zpt`, NRPT / resolved.
- [ ] Gossip RoomConfig и CRL между пирами.
- [ ] DHT-поиск пиров, публичный bootstrap-список.
- [ ] Controller-in-client: `zpt room create --local`, репликация между со-админами.
- [ ] Бэкап/экспорт корневого ключа комнаты (зашифрованный паролем файл + QR).

**Демо**: выключить контроллер на 7 суток (в тесте — ускоренные часы) → комната работает, новые эндпоинты находятся через DHT, сертификаты продлевает со-админ.

## 4. Тестирование

| Уровень | Что | Как |
|---|---|---|
| Unit | pki, acl, magicsock-демукс, парсеры | `go test`, table-driven, `go test -fuzz` для всего, что разбирает сетевые данные |
| Интеграционные | узел ↔ контроллер ↔ relay | in-process, `httptest`, userspace TUN (netstack) — без root |
| e2e сеть | NAT-типы, exit, kill switch, broadcast | Linux netns-стенд в CI (привилегированный runner), сценарии на Go |
| e2e Windows | служба, Wintun, маршруты, WFP, NRPT | self-hosted Windows runner или VM, nightly |
| Нагрузка | 250 узлов в комнате, 50 комнат на узле, 1 Гбит/с через direct | netns-кластер, iperf3, pprof |
| Безопасность | подделка сертификатов, replay конфигов, чужая комната через relay | отдельный набор негативных тестов |

Целевые метрики: пропускная способность direct ≥ 80 % от голого WireGuard-go; время подключения ≤ 5 с (relay) / ≤ 15 с (direct после пробивки); CPU простоя ≤ 1 %.

## 5. Безопасность (чек-лист)

- [ ] Приватные ключи узла — только у службы (Windows ACL, Linux `0600 root`).
- [ ] Корневой ключ комнаты по умолчанию хранится на контроллере зашифрованным (KEK из конфига/ENV); опция «держать офлайн».
- [ ] Все подписи — проверка перед разбором содержимого; ограничение размеров сообщений.
- [ ] Монотонные версии конфигов (защита от отката), короткие сроки сертификатов.
- [ ] Relay не может читать трафик и не пускает узлы без сертификата.
- [ ] Панель: Argon2id, 2FA, CSRF, CSP, rate limit, аудит всех изменений.
- [ ] Exit: по умолчанию выключен; включается только одобрением админа; клиенты exit — только с правом `exit_allowed`.
- [ ] Подписанные релизы и автообновления.
